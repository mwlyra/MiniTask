# Compatibility and limitations

## Windows and runtime

Primary target: **Windows 11 x64**. The available validation host identifies as **Windows 11 Pro 25H2, build 26200.9445**, x64. Its registry retains the legacy `Windows 10 Pro` product string; the build and display version identify Windows 11. See TEST-RESULTS.md for the checks actually executed.

MiniTask targets **.NET 10 LTS**, tested here with SDK 10.0.401 and runtime 10.0.12. Microsoft's .NET 10 support list includes supported Windows 11 editions and certain Windows 10 Enterprise/IoT LTSC releases. Windows 10 APIs are supported by the implementation, but **no Windows 10 build was tested here**. Do not infer official support for ordinary Windows 10 22H2 Home/Pro from runtime installability. Use a Windows edition still covered by the runtime's current OS support policy.

Sources: [.NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy), [.NET 10 supported operating systems](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md), [install .NET on Windows](https://learn.microsoft.com/en-us/dotnet/core/install/windows).

## Input boundaries

- Ordinary applications, browsers and Explorer are the intended targets. Some applications and games ignore or reject simulated input. There is no universal game compatibility claim.
- Windows limits input injection across privilege boundaries. Elevated targets may require an explicitly elevated MiniTask. `SendInput` failure does not identify UIPI as the exact cause, so the error suggests checking privileges without asserting a diagnosis.
- Secure desktops, UAC prompts, sign-in screens and other sessions are unsupported. Playback targets the current interactive desktop.
- No background/minimized-window playback, anti-cheat bypass, stealth, process injection, kernel drivers or security-boundary workarounds are included.
- Remote desktops, fullscreen modes and display changes can affect focus, timing, coordinates and injected-event metadata. The validation host refused foreground activation for the guarded live-input harness; these scenarios require interactive acceptance testing.
- Mouse input records cursor positions, not Raw Input motion. It is not intended to reproduce first-person camera movement. Experimental relative/raw mouse mode was deliberately omitted because it could not be properly validated.
- Keyboard playback uses scan codes when available; Pause uses virtual-key fallback. Layout metadata detects changed layouts. Caps Lock, Num Lock, AltGr, dead keys, IMEs, language modes and target app behavior may still change the resulting text. Physical keystrokes are not a text-insertion API.
- Input reported as injected by Windows, and input carrying MiniTask's marker, is excluded from recording. Input generated by other automation/accessibility software may therefore not be captured.

Source: [Microsoft SendInput documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

## Stop and cleanup

Recording, playback and stop run independently of WPF rendering. Cancellation is checked between events and during deadline waits; environment checks during playback waits occur at most 25 ms apart under ordinary scheduling. The target is detection within 100 ms under ordinary load, **not a hard real-time guarantee**.

Windows can silently remove a low-level hook if its callback times out. The callbacks do not wait for capture processing; they enqueue into a bounded channel, but severe OS scheduling stalls still cannot be ruled out. `RegisterHotKey` also provides a message-loop path; the physical hook is needed for control keys while modifiers are held. If global registration fails, a warning is shown. Resolve it and test stop before using a macro.

Source: [Microsoft low-level keyboard hook requirements](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc).

MiniTask tracks only inputs injected by the current run. It attempts releases on completion, cancellation and handled failures. It does not release a key/button that the hook currently identifies as physically held by the user. If you physically hold an input used by a macro, playback stops; your physical hold remains yours to release. Unrelated physical modifiers may also alter typing, so leave physical input alone during playback. Hook loss, remote input transformations and forceful process/system termination can prevent reliable cleanup.

Session lock, suspension and display-change notifications request stop. Playback never resumes automatically. Cleanup may wait for Windows to schedule the process after suspension. A failed cleanup explicitly tells you to release macro keys/buttons manually.

## Files and omitted features

`.minitask` is a MiniTask-specific, versioned declarative JSON format. There is **no TinyTask `.rec` compatibility**, standalone executable macro export, scripting, scheduling, OCR, AI, plugins, cloud sync or text-insertion feature. The entire application executable is portable; an individual saved macro is a data file, not an executable.

Successful injection means Windows accepted input, not that the target application performed the intended action. Confirm important results in the target application.
